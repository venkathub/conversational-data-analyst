# Conversational Data Analyst

Ask business questions about a bank's data in plain English and get back an answer as text, a table, a KPI card, a bar chart or a line chart, with copy buttons for the answer, the data (TSV) and the chart (JSON).

Repo: https://github.com/venkathub/conversational-data-analyst

```
"Which branches have the highest rejection rate?"
        │
        ▼
   LLM  ──►  JSON query plan (never SQL)
        │
        ▼
   Server validates the plan against a whitelist catalog
        │
        ▼
   Server builds parameterised SQL ──► read-only SQLite ──► result + chosen visualisation
```

## Setup

Requirements: Node.js and npm. Developed and tested on Node 24 / npm 11; older versions (Node 20+) are expected to work but were not tested.

```bash
git clone https://github.com/venkathub/conversational-data-analyst.git
cd conversational-data-analyst
npm install
npm run seed      # creates backend/data/bank.db (deterministic, seed 42)
npm run dev       # API on http://localhost:3001, UI on http://localhost:5173
```

Open http://localhost:5173 and click an example question.

**LLM provider.** With no API key the app uses a built-in rule-based mock, so everything works offline. To use Anthropic, copy `.env.example` to `backend/.env` and set `ANTHROPIC_API_KEY`. The file is git-ignored; never commit it.

| Variable | Purpose | Default |
|---|---|---|
| `ANTHROPIC_API_KEY` | Enables the Anthropic provider when non-blank | blank (mock) |
| `ANTHROPIC_MODEL` | Model id for the Anthropic provider | `claude-sonnet-5-5` |
| `PORT` | API port | `3001` |
| `DB_PATH` | SQLite file, relative to `backend/` | `data/bank.db` |
| `SEED` | Seed for the data generator | `42` |
| `CORS_ORIGIN` | Allowed browser origin (read from the process environment, not listed in `.env.example`) | `http://localhost:5173` |

Other commands: `npm test` (all workspaces), `npm run typecheck`, `npm run build` (frontend bundle), `npm run seed` (reset the data; safe to repeat).

## Architecture

npm workspaces monorepo with a clear frontend/backend split and one shared types package.

```
backend/   Express + TypeScript + zod
  src/db/        schema.sql, deterministic seed, read-only connection
  src/catalog/   whitelist of tables, columns, metrics, dimensions, filters
  src/llm/       LlmProvider interface, MockProvider, AnthropicProvider
  src/query/     planSchema (zod), validatePlan, buildSql, execute, chooseViz/answer text
  src/routes/    POST /api/ask, (GET /api/health in app.ts)
  src/errors/    typed AppError; middleware/ has the error handler and rate limiter
frontend/  Vite + React + TypeScript + Recharts
  chat UI, ResultView (text / table / KPI / bar / line), copy buttons, error states
shared/    API types, constants and formatValue(), used by both sides
```

### Request flow

1. The UI posts `{question}` to `POST /api/ask`. The server validates the body with zod (non-empty, max 500 characters, no extra fields).
2. The `LlmProvider` returns a JSON **query plan** (or an `unsupported` marker). The plan is treated as untrusted.
3. `parseLlmPlan` (strict zod schema) and `validatePlan` check every name against the catalog.
4. `buildSql` produces a single parameterised `SELECT`. Identifiers and expressions come only from the catalog; every value, including `LIMIT`, is a bound parameter.
5. The query runs on a **read-only** SQLite connection. The server picks the visualisation (KPI / table / bar / line), writes a short summary from the actual result, and returns `{ok, answer, viz, columns, rows, meta}`.
6. Failures return `{ok:false, error:{code, message, suggestions?}}` with an appropriate HTTP status. Messages are generic: no stack traces, no SQL.

### Why a query plan instead of SQL

The model is never asked for SQL, so there is no SQL to sanitise. A plan is a small structure: a table, 1–3 metrics, 0–2 dimensions, up to 6 filters, optional sort and limit. The server looks each name up in the catalog and rejects anything unknown (decision 4: no silent clamping or dropping). Prompt injection or a hallucinated column can at worst produce a rejected plan or a harmless valid query.

### Data

Four tables forming three logical datasets, generated by `backend/src/db/seed.ts` with a seeded PRNG (mulberry32; same seed gives identical data, no network or LLM involved):

- `branches` and `customers`: 12 branches in 4 regions; 300 customers (60% Retail, 30% SME, 10% Corporate).
- `onboarding_applications`: 1,500 applications over 24 months ending 2026-06-30 (a fixed reference date, not "today"). Each branch has its own rejection rate (about 5% to 35%); volume has a gentle upward trend plus seasonality that differs by segment.
- `transactions`: 8,000 rows with log-normal amounts scaled by segment, so a few customers dominate the top 5. Only customers with an approved application transact, and only after approval.

### Example questions

| Question | Plan | Shown as |
|---|---|---|
| Show monthly onboarding applications by customer segment | `onboarding_applications`, `application_count` by `month` x `segment` | line chart |
| Which branches have the highest rejection rate? | `rejection_rate` (rejected / decided) by `branch`, sorted desc | bar chart |
| Compare retail and SME onboarding volumes | `application_count` by `segment`, filtered to Retail and SME | bar chart |
| Show the top five customers by transaction value | `transactions`, `total_amount` by `customer`, sort desc, limit 5 | bar chart + table |
| How many onboarding applications are there? | `application_count`, no dimension | KPI card |

## Assumptions

- Single user, no authentication, trusted network.
- Data is synthetic. Currency is shown as INR (₹, Indian digit grouping) because branch cities and names are Indian; amounts have no unit in the schema.
- A customer record is created at their first onboarding application; a customer can have several applications (for example per product).
- Rejection rate = rejected / (approved + rejected); pending applications are excluded from the denominator.
- Each question is answered on its own: the chat shows history, but earlier turns are not sent to the model.
- The Anthropic key lives in `backend/.env` and is provided by the operator.

## Completed functionality

- Chat UI with example questions, loading state, Enter to send, 500-character limit.
- Table selection, query planning, validation, safe SQL building and execution for four tables with 12 metrics and 19 dimensions (see `backend/src/catalog/index.ts`).
- Text, table, KPI card, bar chart and line chart results, chosen automatically.
- Copy buttons: answer text, data as TSV (raw values, formula-safe), chart output as JSON (the exact spec that is drawn).
- Friendly handling of out-of-scope questions (with suggested questions), malformed requests, provider failures and network problems, with retry for transient errors.
- Anthropic provider (tool use, timeout, error mapping) with an offline mock fallback.
- Deterministic seed script, schema, `.env.example`.
- Tests: 92 backend and 10 frontend, all passing at the last commit (seed integrity and determinism, validator and builder guardrails including injection strings, read-only enforcement, provider mapping with a fake client, API end to end with the mock, chart/TSV/error helpers).

## Known limitations

- **Live Anthropic calls were not exercised.** The key is held by the repo owner and was never read by the tooling that built this. The provider is tested against a fake client only; the first run with a real key should be checked by hand.
- The mock understands keyword patterns, not language; unusual phrasing returns "cannot answer".
- Questions are limited to what the catalog expresses: aggregations by up to two dimensions with simple filters. No free-form joins, raw row listing, nested aggregates, percentiles or relative dates such as "last month".
- Strict validation means a slightly wrong plan is refused rather than repaired; the user must rephrase.
- No conversation memory across turns, no streaming, no saved sessions.
- In-memory rate limiter (per process); no authentication or per-user quotas.
- `npm audit` reports advisories: zod 3.x (memory use on oversized arrays; mitigated by the 10 KB body limit and schema caps, upgrade to zod 4 recommended) and vitest/esbuild tooling (development only). They were not upgraded to avoid breaking changes.
- Frontend tests cover pure logic (chart shaping, TSV, error mapping); there are no component or browser end-to-end tests. UI behaviour was checked manually in a browser.
- The production bundle is about 500 kB because of Recharts (Vite reports a size warning).

## Productionising

- **Security:** authentication (SSO/OIDC), authorisation per table or row, per-user rate limits in a shared store, HTTPS, strict CSP, secrets manager instead of `.env`, dependency scanning in CI.
- **Data:** move from SQLite to Postgres or a warehouse using a read-only role on a replica with statement timeouts and row limits; migrations; column-level masking for PII.
- **LLM:** evaluation suite of questions with expected plans, prompt/model versioning, prompt caching, cost and latency tracking, retries with backoff and a circuit breaker, conversation context for follow-ups, human-readable plan explanations.
- **Operations:** structured logging with request ids (never logging questions or secrets by default), metrics and tracing, health/readiness checks, Docker images, CI (typecheck, test, build) on every push, staged deploys.
- **Product:** saved questions and dashboards, CSV/PNG export, catalog managed as configuration with a review workflow (the `add-metric` project skill documents the current process).

## AI disclosure

**Tools used:** Claude Code (Anthropic's coding agent, running a Claude Sonnet model) wrote the code, tests, skills and documentation in this repository from a written plan, running the tests, the API and the UI in a browser as it went. Claude is also the runtime LLM provider when an API key is configured.

**Decisions made by the project owner (not by the AI):**

1. The LLM returns a JSON query plan, never SQL; the server validates it against a whitelist catalog and builds parameterised SQL itself.
2. Use Anthropic when `ANTHROPIC_API_KEY` is set, with a rule-based mock fallback; the owner supplies the key in `backend/.env`, and only `.env.example` with a blank value is committed.
3. Stack: Express + TypeScript + zod backend; Vite + React + TypeScript + Recharts frontend; SQLite via better-sqlite3, read-only at query time; Vitest; npm workspaces (backend, frontend, shared).
4. `validatePlan()` rejects strictly: any unknown table, column or filter, or an out-of-range limit, returns a clear "cannot answer" error and nothing is clamped silently.
5. The GitHub repository is public and named `conversational-data-analyst` under the `venkathub` account.

**Left to the AI within that plan:** the exact plan shape and catalog contents, the synthetic data generator's details, the mock's keyword rules, the Anthropic prompt and tool definitions, response format, chart/table selection rules, UI design and the rate limiter. These were reviewed through tests and manual runs, not independently audited.
